# analyze-browser-security

ブラウザは、利用者の手元で動く、利用者が自由に書き換えられる場所である。この層の分析は、二つの向きを分けるところから始める。一つは、ブラウザを通して利用者が攻撃される向き（他サイトや注入されたスクリプトが、利用者の権限で何かをする）。もう一つは、利用者がブラウザを通して攻撃する向き（画面を通らずに要求を組み立てる）である。前者はブラウザの仕組みで守れるが、後者はブラウザの中では守れず、守りはサーバーかデータの読み取り規則にしか置けない。二つを混ぜると、画面で隠しただけのものを守ったことにしてしまう。

## 守るものの資料から始める

入力の守るものの資料が、何を誰から守るかを持つ。この入口は守るものを決め直さない。守るもののうち、ブラウザに届く情報、ブラウザが持つ資格情報（Cookie、トークン、招待の値）、ブラウザから始まる操作を拾い、それぞれに届く攻撃の経路を考える。資料に無い守るものに気付いたら、自分で足さず、守るものの資料への提案として返す。

## 判断の要

**ブラウザに届いたものは、全て読まれる。** 画面に出さない値、難読化したコード、ブラウザから直接読めるデータベースやストレージは、利用者が開発者ツールで読む。ブラウザが直接データを読む構成では、守りはそのデータの読み取り規則だけになる。その規則で誰に何を許すかは認可の判断で、analyze-server-security が持つ。この層では、ブラウザから画面を通らずに届く経路（データの直接の読み取りと購読、画面が使わない API の呼び出し）を全て挙げて、その分析へ渡す。

**スクリプトが注入されたときの被害は、そのスクリプトが届く範囲で決まる。** XSS の対策は、注入させないこと（出力の文脈に合ったエスケープ、危険な API を使わない）と、注入されたときに届く範囲を狭めることの二段で考える。HttpOnly の Cookie はスクリプトからの読み出しを防ぐが、スクリプトがその Cookie 付きで要求を送ることは防がない。CSP は外への送信先や読み込み元を絞れるが、同じオリジンの API を使った持ち出しと、自サイトから配った依存パッケージのスクリプトは止めない。どこまで期待できるかを書き、期待できない分を別の守りへ渡す。

**CSRF が成り立つかは、資格情報が自動で送られるかで決まる。** Cookie で認証する入口は、他サイトから利用者の資格情報付きで要求を送れるので、状態を変える入口に対策が要る。Authorization ヘッダーだけで認証する入口は、ブラウザが自動で付けないので構造的に成り立ちにくい。ただし、ログインそのもの（ログイン CSRF）と、GET で状態を変える入口は別に確かめる。CORS は読み出しを許すかの設定で、要求が届くことは止めない。入口ごとの保護の宣言は development-convention の `protect-entry-points` が持つので、ここでは層としての方針と理由だけを書く。

**秘密の値を URL に載せない。** URL は、履歴、サーバーと中継のログ、他サイトへの参照元、チャットのリンクのプレビューに残る。認可コード、トークン、招待の値は、本文かフラグメントで運ぶ。

**端末と通知に残るものも漏えいの経路である。** 共用の端末に残るログインの状態とキャッシュ、ロック画面に出る通知の文面は、利用者の外の人に届く。通知の文面に、誰と何をしているかが分かる情報を入れない。

**フロントエンドの依存パッケージは、自サイトの権限で全利用者のブラウザで動く。** 乗っ取られた依存は、XSS と同じ被害を全利用者に一度に与える。版の固定、公開直後の版を待つ、インストール時のスクリプトを止めるといった供給経路の守りは、インフラの分析の CI の守りと重なるので、どちらの資料が持つかを書き、二重に書かない。

## 費用とトレードオフ

対策の多くは無料だが、利便性を下げるもの（ブラウザを閉じたら消えるログイン、厳しい CSP による実装の制約、Trusted Types の導入）と、費用がかかるもの（WAF、外部の検査サービス）は、得るものと失うものを並べ、守るものの優先順位から推奨を置いて、grill の公開入口で利用者に問う。返った決定は理由とともに資料に書き、未決は推奨を仮に置いたことが分かる形で書く。

## 資料の形

冒頭に、この層で最も危ない経路と、それを止める守りを言い切る。ブラウザ、サーバー、データの読み取りの間の信頼の境界と、資格情報の流れの図を置く。続けて、守るものごとの攻撃の経路と対策、採らない対策とその理由、残るリスク、公開前に確かめる試験、確かめていない仕様を書く。資料は write-doc の公開入口に、素材と保存先を渡して保存する。

## 入力

守るものの資料の絶対パス、対象の構成の資料かコードの絶対パス、資料の保存先（新しく作るなら保存先のディレクトリと名前、書き直すなら既存の資料の絶対パス）を受け取る。

## 止まるとき

この資料の結論は、ブラウザを通る経路ごとの守りと残るリスクである。守るものの資料が無いときは止まり、decide-what-to-protect で先に作るよう返す。ブラウザで動く部分の構成（認証の方式、データの読み方）が入力から分からず守りが決まらないときも、止まって必要な入力を返す。保存先が絶対パスで一つに決まらないとき、write-doc か grill が失敗したときも止まる。

## 返すもの

保存した資料の絶対パス、最も危ない経路と守り、利用者が決めたこと、推奨を仮に置いた未決、守るものの資料への提案を返す。
