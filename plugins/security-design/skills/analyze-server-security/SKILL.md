# analyze-server-security

サーバーサイドは、利用者が自由に組み立てた要求を受け取る最後の場所である。この層の分析は、「画面はこう使われるはず」という前提を全て外し、守るものに届く要求を、正規のアカウントを持つ利用者が組み立てられる範囲で考える。多くの穴は、技術的な脆弱性ではなく、業務の決まりがコードのどこにも強制されていないことから生まれる。だから、守るものを業務の不変条件として書き、それをどこで強制するかを決めることが、この層の中心になる。

## 守るものの資料から始める

入力の守るものの資料が、何を誰から守るかを持つ。この入口は守るものを決め直さない。守るもののそれぞれについて、それを読む、変える、順序を崩す要求がどこから届くかを考える。資料に無い守るものに気付いたら、自分で足さず、守るものの資料への提案として返す。入口（RPC、HTTP、Webhook、ジョブの受信口）ごとの認証、認可、利用上限、偽装要求への対策の宣言は development-convention の `protect-entry-points` が持つ。この入口は、その宣言の中身を書き直さず、層としての方針と、宣言が要る入口を挙げて渡す。

## 判断の要

**認可は、入口ではなく、守るものに触れるたびに確かめる。** 入口で「ログインしている」を確かめても、その要求が指す対象（他人の注文、他国の会話）に触れてよいかは別である。対象の ID を要求から受け取る箇所は全て、その主体がその対象に触れてよいかを確かめる。一覧の取得、更新、削除、横断の問い合わせ、ブラウザが直接読むデータの読み取り規則も同じである。読み取り規則は「どれか一つが許せば通る」形が多く、広い規則が狭い規則を無効にするので、全てを拒否してから許す経路を足す。読まれる情報は中身だけではない。ある記録が存在するか、何件あるか、いつ更新されたか、拒んだときの応答の違いからも、守るもの（誰が誰と話しているか、命令を出したか）が分かる。権限は状態で変わる（参加者が脱落する、ゲームが終わる、所属が外れる）ので、トークンに埋めた値ではなく、その時点の状態で判定する。

**業務の値は、作るときに一度だけ検証し、検証した型で運ぶ。** 文字列や数値のまま運ぶと、検証したかどうかが呼び出しごとに変わる。業務の意味を持つ値（金額、数量、国、メールアドレス）は、作るときに不変条件を確かめた型（ドメインプリミティブ）にし、それ以外の形で業務の処理に入れない。有効な値は、外部の標準の最も広い定義ではなく、その業務の文脈の意味で決める。検証は、安い確かめから順に行う。出所（信頼できる送り手か）、大きさ（全体と項目ごとの両方）、字句（使える文字か）、構文（形が正しいか）、意味（業務として成り立つか）の順にすると、重いパーサー、正規表現、データベースを攻撃者に使わせる前に、多くを安く拒める。検証の前に値を直さない。直す処理が、無害な値を攻撃の値に変えることがあるからである。存在するか、その状態から遷移できるかという意味の確かめは、入口の検査ではなく業務のモデルが持つ。

**不正な状態を作れないようにする。** 状態を持つものは、許される状態の遷移だけを操作として持ち、任意の項目を外から書き換えられる形にしない。要求の項目をそのままモデルへ写すと、利用者が送った余分な項目（権限、所有者、価格）で状態が変わる（マスアサインメント）。

**順序と時刻は、完全性の一部である。** 締切、在庫、残高、一度だけの操作のように、確かめてから使うまでの間に状態が変わり得るものは、確かめと変更を一つのトランザクションか、同じ状態を読む直列の処理に入れる。重複を防ぐ一意の ID は、送信者ごとに区切る。区切らないと、他人の ID を指定して相手の操作を握りつぶせる。時刻はサーバーの時刻で判定する。抽選、割り当て、招待やトークンの値のように、当てられると不公平や乗っ取りになる値は、予測できない乱数で作る。

**非同期の処理は、受け取った中身を信じない。** キューやスケジューラから届く中身は、送り手が乗っ取られれば任意の値になる。中身は手掛かりとしてだけ使い、状態と権限はデータベースで確かめ直す。

**認証を自作する部分は、仕様の確かめを全て自分で持つ。** OAuth や OpenID Connect を自分で組むと、`state` と `nonce` の照合、PKCE、ID トークンの発行者と宛先の検証、認可コードとトークンをログと URL に残さないことが、全て自分の責任になる。署名付きトークンの検証の順は `protect-entry-points` が持つ。

**外へ出すものは、必要な分だけにする。** エラーの応答に内部の情報を載せず、拒んだ入力の値をそのままメッセージ、例外、ログへ写さない。写した値は、それを表示する別のシステムでコードとして解釈され得る。業務の失敗と技術の失敗は別の型にし、技術の例外に業務のデータを入れない。ログは出す項目を明示的に選ぶ。オブジェクトを丸ごと出すと、後から足した項目まで漏れる。ログにトークン、秘密の値、利用者の本文を書かない。秘密の値は、ログや例外の表示へ漏れない型で持ち、一度読んだら使い捨てる。外部の URL を受け取って取りに行く処理は、内部のアドレスやメタデータのエンドポイントへ届かないようにする（SSRF）。データベースやシェルへ渡す値は、組み立てずに引数として渡す（注入）。

**応答をキャッシュに残させない。** CDN や中継が個人の応答を保存すると、認可が全て正しくても、別の人に返る。個人の応答には、保存させない指定を強制する。

## 費用とトレードオフ

認可の網羅的な試験、解決の試験集、外部の検査サービス、記録の増加（不正を見つけるために持つ情報が増える）は、得るものと失うものを並べ、守るものの優先順位から推奨を置いて、grill の公開入口で利用者に問う。返った決定は理由とともに資料に書き、未決は推奨を仮に置いたことが分かる形で書く。

## 資料の形

冒頭に、この層で最も危ない穴と、それを止める守りを言い切る。要求が入口から守るものへ届くまでの流れと、認可と検証を置く場所の図を置く。順序が守るものに関わるなら、確かめと変更の順を時間の流れで描く。続けて、守るものごとの攻撃の経路と対策、採らない対策とその理由、残るリスク、公開前に確かめる試験（読めないこと、変えられないことの否定の試験を含む）、確かめていない仕様を書く。資料は write-doc の公開入口に、素材と保存先を渡して保存する。

## 入力

守るものの資料の絶対パス、対象の構成の資料、業務の資料、コードのどれか一つ以上の絶対パス、資料の保存先（新しく作るなら保存先のディレクトリと名前、書き直すなら既存の資料の絶対パス）を受け取る。

## 止まるとき

この資料の結論は、守るものごとの認可と不変条件をどこで強制するかと、残るリスクである。守るものの資料が無いときは止まり、decide-what-to-protect で先に作るよう返す。守るものに触れる処理が入力から分からず、強制する場所を決められないときも、止まって必要な入力を返す。保存先が絶対パスで一つに決まらないとき、write-doc か grill が失敗したときも止まる。

## 返すもの

保存した資料の絶対パス、最も危ない穴と守り、`protect-entry-points` で宣言が要る入口、利用者が決めたこと、推奨を仮に置いた未決、守るものの資料への提案を返す。
